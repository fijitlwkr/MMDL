## 6. 3단계 런처의 length 중단 검사 수정과 영향

수정 대상은 우리 운영 런처 judge_runner.py의 소량 시험 검사였다.
최초 E1 5건 중 1건은 HTTP 200이지만 **Judge 응답**의 finish_reason=length였고,
런처가 모든 시험 응답에 stop을 강제해 저장 후 중단했다.
이는 모델 생성 raw의 length 종료를 차단하는 게이트 변경이 아니다.

frozen v2 evaluator는 원래부터 Judge 비정상 종료·Z·빈 답을 완료된 추출 실패/오답으로 처리한다.
런처의 stop 강제만 제거하고 snapshot·응답 수·evaluator 스키마 검증을 따르도록 수정했다.
check_env·평가 코드·config·정책·Judge max_tokens=8·문항별 판정은 그대로다.
해당 1건은 여전히 추출 실패/오답이며 재호출하거나 정상 응답으로 교체하지 않았다.
새 창에서는 저장된 5건을 재사용해 E1 나머지 64건과 E2 39건만 호출했다.

[최초 캐시 검증](scoring_20261101/pilot_cache_verification.json)에서 최초 5응답,
HTTP receipt, 최초 10 journal 이벤트의 바이트 prefix SHA-256 보존을 확인했다.
총 API 시도/응답은 E1 69/69, E2 39/39(중복·API 오류 0)이다.
E1 Judge 종료는 stop 68 /length 1, E2는 stop 39이고 모두 pending=0이다.
따라서 운영 재개 검사의 수정은 완료 시점에만 영향을 주었고 채점 규칙·저장 응답·점수에는 영향이 없다.
API usage 비용은 기존 기록대로 E1 $0.0545484 /E2 $0.0046224, 합계 $0.0591708이다.
이 단계의 API 비용은 0이다.
